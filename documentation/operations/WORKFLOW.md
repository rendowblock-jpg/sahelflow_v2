# SahelFlow — Research, coding, review and delivery workflow

> **Status:** Active operating contract
> **Governing decisions:** FD-028; FD-029; FD-030; FD-032; FD-033
> **Execution mode:** one active application implementation owner; audit-first; large coherent Internal.16 completion wave; targeted coding checks; frozen full-product certification; consolidated repair
> **Durable truth:** protected `main`, branches, PRs, Actions, releases, issue #164 and active documentation authorities
> **Last consolidated:** 2026-08-13

This workflow exists to finish SahelFlow quickly without turning speed into hidden
product risk. The default process remains research/impact-map → coherent implementation
→ frozen review/evidence. FD-033 adds an exact Internal.16 deadline mode that groups
remaining whole-product work into one controlled convergence rather than many tiny
release loops.

Speed never comes from weakening business integrity, AppData preservation, security,
privacy, Arabic/RTL, accessibility, low-end performance, recovery, provider truth or
evidence honesty.

## 1. Roles and write ownership

### Founder

The Founder sets product/commercial decisions, selects the active coding owner,
controls signing/payment ceremonies, observes installed milestones and explicitly
promotes Beta/Stable.

### Active application implementation owner

Only one agent owns shared application writes at a time. That owner:

- reconstructs exact live GitHub authority before editing;
- completes the applicable research/impact map;
- owns one branch/frontier;
- preserves Phase 1–4 canonical authority;
- runs targeted checks during implementation;
- freezes the candidate before full review/certification;
- records evidence at the level actually observed.

### Other agents/reviewers

Other agents may perform read-only reconnaissance, review, research, test analysis,
commercial preparation or documentation work when it does not create competing
application writes. They do not silently edit shared contracts or a live implementation
branch owned by another agent.

### Desktop/Windows evidence

Installed evidence owns MSI/updater/WebView/process lifecycle, AppData/registry/key
preservation, actual UI observation and T470/floor performance/reliability.

### GitHub/Actions

Protected `main` is integrated source truth. Branches/PRs are proposals. Actions is
clean-checkout source/artifact evidence, not a coding agent. Releases bind exact source,
version, signature, artifacts and publication evidence.

## 2. Core anti-drift rules

1. One active application writer at a time.
2. No direct protected-main application edits.
3. No material implementation without an impact map/Problem Register appropriate to
   the frontier.
4. Shared schema/migration/identity/permission/command/event/provider/design contracts
   are frozen before dependent implementation.
5. No important decision remains only in chat.
6. `CURRENT_STATE.md` owns current source/evidence truth; `ROADMAP.md` owns program
   sequencing; this file owns process; `WORKING_MEMORY.md` owns compact next action.
7. A page/model/adapter/mock/passing unit test does not complete a capability.
8. Arabic/RTL, accessibility, recovery and performance are continuous requirements.
9. Provider/security/performance/AAA/Stable claims never exceed evidence.
10. Do not create a competing permanent masterplan or gap-report system.
11. Never delete/reset unrelated Founder work, AppData, registry, databases, keys or
    retained evidence to simplify testing.
12. Never rerun an unchanged passing exact head for ritual.
13. Never retry a deterministic product failure until it becomes green without a
    diagnosis and correction.

## 3. Standard session purposes

A work period declares one primary purpose:

- governance/documentation;
- research/contract;
- implementation;
- frozen review/closure;
- installed/release evidence.

FD-033 Internal.16 is allowed to span multiple implementation outcomes inside one
branch/frontier, but the branch still has one application owner and one frozen final
candidate.

## 4. Start/resume protocol

Before application writes:

1. re-fetch protected `main`, open PRs/issues, exact heads and Actions;
2. verify the previous release/installed truth instead of assuming it;
3. read AGENTS, documentation entry point, governing decisions, Current State, Roadmap,
   Workflow and Working Memory;
4. inspect exact production source/tests/migrations/callers for the affected surface;
5. preserve unrelated work/evidence;
6. complete the required reconnaissance and Problem Register;
7. freeze shared contracts, acceptance matrix and non-goals;
8. declare branch, owner and evidence plan.

## 5. Research/contract rule

Use primary/current authority for unstable external facts: official platform/provider
API docs, standards, law, security advisories and current framework/runtime docs.
Inspect SahelFlow source first. Research is bounded: once enough evidence exists to make
a safe implementation decision, implement.

For provider/platform work record:

- exact contract/version/date;
- credentials/secret boundaries;
- retries/rate limits/idempotency/ambiguity semantics;
- unsupported capabilities;
- conformance versus live-certification state;
- revalidation trigger.

No guessed endpoint or inferred success contract becomes production authority.

## 6. Whole-product reconnaissance and Problem Register

The audit covers, where applicable:

- every production caller/route/page/command/background consumer;
- business/stock/money/provider/idempotency/version/audit authority;
- models/migrations/indexes/backup/restore/replacement-install implications;
- identity/shop/permission/reauth/secret/privacy boundaries;
- loading/empty/validation/permission/offline/stale/pending/conflict/error/retry/
  recovery/history/bulk states;
- AR/FR/EN, Arabic/RTL/mixed content, keyboard/focus/semantics/zoom/reduced motion;
- 1366×768/responsive containment, charts/tables/forms/dialogs;
- unit/integration/database/browser/Rust/Windows/installed tests;
- diagnostics/observability/security redaction;
- startup/query/render/mutation/resource/long-session performance;
- exact CI/release/evidence artifacts.

Each Problem Register item records severity P0–P3, journey, root cause, authority,
dependencies, correction, tests/evidence, owner and closure state. Group by root cause.

## 7. FD-033 Internal.16 deadline completion mode

This mode applies only to the exact completion frontier authorized by FD-033.

### 7.1 Before implementation

Perform one whole-product reconnaissance and freeze one consolidated Internal.16
Problem Register covering:

- remaining Phase 5/6/7 route/system gaps;
- all Phase 8 required outcomes;
- NOEST removal and EcoTrack Pro migration/integration;
- AI workspace, extraction and every model-exposed tool;
- installer/updater/licensing/recovery/cloud/security/privacy/evidence implications.

Do not begin with random screenshot fixes or the first failing test.

### 7.2 Large implementation wave

After contracts are frozen, implement dependency-correctly in large coherent batches.
A batch may span many files/layers when they deliver one complete product subsystem or
remove one shared root cause.

During coding use **cheap targeted checks**, for example:

- changed-scope TypeScript/ESLint;
- focused Vitest/domain/database suites;
- targeted provider conformance;
- targeted Playwright for changed journeys;
- Rust format/check/tests when native code changes;
- schema/version/audit checks when those authorities change.

Do not trigger a full MSI + replacement-install + complete browser matrix + eight-hour
soak for every small edit. Heavy evidence belongs to the frozen candidate unless a
high-risk native/data/recovery change needs earlier proof.

A proven P0 stops the wave. A P1 may be fixed inside the wave but cannot survive
candidate freeze/release.

### 7.3 Candidate freeze

Once all planned Internal.16 implementation is present:

- stop feature expansion;
- run diff/legacy/stale-authority review;
- freeze exact head;
- run one complete adversarial review across every affected layer;
- run the full certification matrix.

The first full pass must return the complete actionable finding set rather than forcing
one-assertion-at-a-time discovery.

### 7.4 Consolidated repair

Repair the complete supported finding set in one dependency-correct batch. Re-review
materially changed areas. Rerun affected heavy evidence plus one final complete
certification of the repaired candidate.

Do not create an artificial Internal.16 → .17 → .18 sequence merely because each
finding was discovered separately. A later hotfix remains allowed if a genuine
post-release defect is discovered; Internal.16 is nevertheless built as the complete
candidate, not an intentionally unfinished stepping stone.

## 8. Internal.16 AI/extraction/tool assurance

### AI workspace

Test desktop/mobile workspace structure, long sessions, session switching, streaming,
cancel/retry/reconnect, provider/key/consent/quota/persistence/degraded states, action
review, typed tool cards, AR/FR/EN, RTL/mixed direction, keyboard/focus, zoom/reflow,
reduced motion and low-end rendering/resource behavior.

### Order extraction

Use a held-out benchmark corpus representative of Algerian COD messages:
Arabic/French/English/Darija/mixed language, noisy WhatsApp formatting, partial,
contradictory, ambiguous and non-order inputs.

Measure:

- field-level exactness/normalization;
- required-field completeness;
- false-complete rate;
- confidence calibration/missing-field truth;
- regex/Gemini routing selection;
- no-key/offline fallback;
- invalid/malformed model output;
- quota/rate-limit behavior;
- regex path, model path and total latency distributions;
- correction/review before canonical order creation.

Extraction output never bypasses canonical order validation, seller review where
required, pricing, risk, inventory, idempotency or business-command authority.

### AI tools/actions

Inventory every model-exposed tool. For each prove:

- schema/arguments;
- actor/shop/permission/license authority;
- proposal/digest approval for sensitive action;
- exact target/version revalidation;
- correct result shape and localized product presentation;
- idempotency and duplicate protection;
- timeout/cancel/retry/ambiguous external-effect handling;
- privacy/redaction and secret boundaries;
- local overhead versus external/model/provider latency;
- bounded concurrency and T470/floor resource impact.

Model/provider latency is not used to hide slow SahelFlow dispatch/database/business
execution. External waits must show honest progress/degraded state rather than freeze or
fabricated success.

## 9. Provider integration workflow — EcoTrack Pro

Internal.16 removes the NOEST product/provider surface and adds canonical EcoTrack Pro.
Before code, obtain or identify the current authoritative EcoTrack merchant contract.
No guessed hosts/endpoints/capabilities.

The implementation must cover all supported contract capabilities needed by SahelFlow,
including protected configuration, connection test, create/validate semantics,
tracking/history, tariffs/reference data, supported fulfillment/update/cancel/return/
document behavior and durable reconciliation after timeouts/unknown outcomes.

Historical `noest` records remain readable; credentials/history are not silently
reinterpreted. Deterministic conformance evidence and live certification remain separate
under FD-030.

## 11. Severity and release blocking

- **P0:** data loss, secret exposure, cross-shop/tenant effect, corrupt update/restore,
  irreversible stock/money damage. Stop immediately.
- **P1:** Required journey failure, authority bypass, duplicate/lost provider effect,
  unsafe migration/startup/install/recovery, major Arabic/UX/accessibility/reliability
  failure. Blocks candidate/release.
- **P2:** bounded hardening issue with safe workaround; cannot be mislabeled as P3 to
  meet schedule.
- **P3:** low-impact polish.

Internal.16 user-ready requires zero known P0/P1. Stable additionally requires its
external/representative Phase 9 evidence.

## 12. Branch/PR practice

- branch from current verified protected `main`;
- Internal.16 has one application implementation branch/owner;
- push coherent batches rather than every tiny edit;
- open a draft PR early once application implementation begins;
- PR body records scope, Problem Register, contracts, preservation, migration,
  provider/AI/cloud implications and evidence;
- freeze exact head before consolidated review;
- merge only with selected gates/review satisfied and expected-head protection;
- ordinary docs/governance branches do not become competing application writers.

## 13. Release/evidence ladder

Truth levels remain distinct:

1. implemented/static source;
2. unit/domain;
3. integration/API/database/provider conformance;
4. controlled UI/browser;
5. clean Actions;
6. signed artifact;
7. installed Windows;
8. T470/floor/soak;
9. external provider/security/privacy/legal/accessibility;
10. representative seller/Beta.

Implemented, source-proven, artifact-proven, installed, Founder-accepted,
user-ready/RC, phase-closed and Stable are not interchangeable.

## 14. Documentation and protected boundaries

At closure update the existing owning authorities, issue #164 and exact evidence. Do
not create another permanent masterplan.

Preserve Founder install evidence, unrelated local changes, canonical AppData,
registry, databases, migrations, keys and protected business authorities. Never make
CI green by deleting evidence/data or weakening tests/thresholds.
