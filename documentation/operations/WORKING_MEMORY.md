The read-only inventory is **complete for package selection**. Orders + confirmation
queue was selected over Dashboard, Customers/Risk, Products/Inventory,

### Why Orders + confirmation queue won

- `/orders` was the controlled Phase 7 route outlier under 4× CPU throttling.
- The list workbench loaded up to 25 orders and then risk projection fanned out
  through per-order order/history/customer/wilaya reads.
- Initial `/orders` render also eagerly loads all customer + active product/variant
  creation data for actors allowed to create orders.
- SWR immediately revalidated the exact server fallback on hydration, duplicating
  the expensive `/api/orders` workbench before the seller changed anything.
- The main list, confirmation queue and detail route preserve strong canonical
  business authority but present it as several assembled implementation surfaces.
- Bulk-governance, order decision and fulfillment copy is fragmented across local
  AR/FR/EN dictionaries/branches rather than one governed Orders copy authority.
- Risk-factor labels are translated, but the pure scoring engine's `factor.explanation`
  is English computational prose and is rendered directly in order detail/create
  warnings, creating real FR/AR presentation leakage.
- Existing broad browser evidence renders `/orders` and confirmation queue but does
  not prove a dedicated create → review/confirm → fulfillment seller journey.

### Families intentionally not selected first

Dashboard, Customers/Risk, Products/Inventory, Delivery/Returns, COD/Accounting,
Analytics, Automations and setup/login/license/remaining administration were all
reviewed. They are not declared complete, but none combined a stronger immediate
route-architecture and measured-performance reason than Orders.
