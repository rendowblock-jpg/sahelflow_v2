# MCP agentic surface study (EX-5) — CodFlow's tool registry mapped onto SahelFlow's proposal-bound authority

> **Status:** Research/comparison input recorded under FD-061. Study/design only — this document authorizes nothing.
> **Source:** `github.com/bighadj22/codflow` @ `00f18fac…` (Apache-2.0), `cod-server/src/mcp/**` read 2026-09-17
> **Standing constraint:** no external agent surface exists in SahelFlow and none ships without a separate explicit Founder decision. Every design statement below is input to that decision, not its implementation.

---

## 1. What CodFlow has (upstream truth at the pin)

**Shape:** a remote, stateless Streamable-HTTP MCP server (`POST /mcp`) in the `cod-server` Cloudflare Worker — `@modelcontextprotocol/server` v2.0.0 + Cloudflare `agents` v0.22.0 `createMcpHandler` + `@cloudflare/workers-oauth-provider` v0.10.3. A fresh `McpServer` is built per request (`legacy: "reject"` — no sessions/Durable Objects); no verified identity ⇒ **zero tools registered** (fail-closed).

**Registry — 96 tools, verified.** `cod-server/src/mcp/registry.ts` holds `TOOL_REGISTRY: { requires: string[], build }[]`; 98 `pick(...)` rows dedupe to **96 unique tools** (listWilayas/listWilayaCommunes deliberately double-registered under two scopes). CI guards pin the count and per-scope tool lists (`registry.test.ts` golden arrays). Flat camelCase names, no prefixes: `listOrders`, `deleteCustomer`, `setShippingCommuneOverride`. Domains: customers 8, orders 8, landing pages 14, shipping profiles 10, stock 7, customer groups 7, customer tags 7, products 6, drivers 6, product groups 5, offers 5, variants 5, reviews 3, driver payments 3, wilayas 2.

**Scope-gated visibility — hidden, not erroring.** `buildToolsForUser` skips any registry entry whose `requires` (AND-ed `domain:action` scopes from `cod-shared/rbac/scopes.ts`, exact match or `*`) the caller lacks — enforced **at registration time so the MCP client cannot even see** tools it may not call. Admin role (or `*`) sees all 96. Grant-side: `computeGrantableScopes` caps a non-admin's consent choices at scopes they hold; the consent page renders per-domain checkbox chips (trilingual ar/fr/en, RTL-aware, CSRF double-submit); zero grantable scopes ⇒ "Nothing to authorize". **No plan/tier gating anywhere.**

**Tool anatomy — two-layer validation + declared outputs.** Domain factories (14 `ai-tools.ts` files) build Vercel-AI-SDK `tool()`s; layer 1 input is permissive so a malformed LLM call never crashes the SDK, layer 2 is the strict Zod schema whose exact `.shape` is merged into `TOOL_SCHEMAS` — *tools/list advertises what execute() validates; drift is test-impossible*. Every tool advertises an `outputSchema` from `toolOutput()`: a Zod union of `{success:true,…payload}` / `{success:false,error}` (`looseObject` payloads). Execution results are safe-parsed against the declared schema; on success both a JSON `text` block **and** `structuredContent` ship; on drift `structuredContent` is omitted but text still ships — a schema bug can never break a working tool. Handled failures and thrown errors both surface as `isError:true` with the same envelope.

**Destructive doctrine — annotate and trust the client.** `annotations.ts` **derives** `readOnlyHint/destructiveHint/idempotentHint/openWorldHint` from membership sets (read-only = read-scope-only tools + one override; destructive = the 23-entry `DANGEROUS_TOOLS` in `elicit.ts`; idempotent = 4 membership tools; open-world = only `uploadLandingPageImage`); consistency is CI-proven. **The server executes destructive tools directly — there is no server-side confirmation round** (test-pinned: "client-side confirmation is the human gate"). A server-side HITL was tried upstream and rolled back (it depended on client elicitation support; a fail-closed fallback would break destructive tools in incapable clients). Human agency lives at (a) consent-time scope grants, (b) client-side confirmation framed by annotations, (c) audit.

**Audit & limits.** Every invocation writes one `mcp.tool_called` activity row with `redactForAudit` (strings >1024 chars elided, depth ≤8), client subject/session; rate limit 200 calls/60 s per subject via KV fixed window, fail-open; pagination `limit`/`offset` (default 50, max 100–200) + `count`, orders additionally keyset-cursor; the only async pattern is image upload (job + poll, Workflow-driven, `openai/fileParams` `_meta` hints); no prompts/resources, no versioning/deprecation flags; `mcp.tool_declined` and the `elicit.ts` filename are stale vestiges of the rolled-back elicitation design.

**Auth.** OAuth 2.1 provider (opaque tokens in KV, `accessTokenTTL` 1 h, refresh 30 d), DCR + CIMD client registration, RFC 9728/8414 discovery (`resourceMetadata.scopes_supported = ALL_SCOPES`), dashboard-login relay via single-use HMAC tickets (5-min TTL, KV nonce replay check), `WORKER_SELF_URL` token-audience binding, instant revocation (grant delete kills live sessions), management REST under session JWT or API key (`mcp:view` scope).

## 2. What SahelFlow has (proposal-bound authority, already protected)

- **Models** (`prisma/models/ai-action-runtime.prisma`): `AiActionProposal` (immutable authority snapshot; only lifecycle columns mutate; `proposalKey`/`proposalDigest` unique) → 1:1 `AiActionApproval` (decision + full approver snapshot, `approvalDigest` unique) → 1:1 `AiActionExecution` (`executionKey` unique, `businessCommandId`). SQLite trigger guards pin the state machines; *succeeded execution is terminal*.
- **Vocabulary** (`src/lib/ai/actions/contracts.ts`): execution classes `read` (19 tools) / `external_read` (2) / `sensitive` (8: `create_order`, `update_order_status`, `update_product_stock`, `cancel_order`, `create_product`, `update_product_price`, `create_customer`, `update_customer_notes`) / `blocked` (1: `assign_order_to_delivery` — registered, never advertised, never executable). `EXPECTED_AI_TOOL_NAMES` is test-pinned (`catalog-invariants.test.ts`).
- **Proposal mechanics**: creation requires a durable *person* actor holding `ai.use` + `approvals.request` + the tool's permissions; args are zod-validated and sealed with the shop business envelope key; the proposal binds to the exact persisted chat message (10-min TTL); `INSERT OR IGNORE` gives creation idempotency; keyed HMAC digests detect tampering (`*_TAMPERED` conflicts).
- **Approval is digest-bound and person-only**: `approveAiActionProposal` requires the exact 64-hex `proposalDigest`; re-validation re-checks shop runtime, expiry, policy drift, requester identity/permissions, license and target snapshots; the approver must hold `approvals.approve` + `ai.use` + **every permission the tool requires**, and is locked to the first approver's identity snapshot (`AI_ACTION_APPROVER_DRIFT`). Replay: stored encrypted result returns with `replayed:true`; the business command rides `idempotencyKey: ai-action:${proposalId}` against the kernel's committed-command ledger.
- **Execution**: `mintAiActionExecutionAuthority` mints an unforgeable branded authority; the executor re-hashes args, runs `executeBusinessCommand` (`commandType: "ai.action.execute.v1"`) — money truth, audit, domain events, reservations and compensations stay inside the kernel. Status gates hold: AI cannot set `confirmed` (`CANONICAL_CONFIRMATION_REQUIRED`); AI orders enter as `source:"ai_chat"` drafts.
- **Remote-narrowing precedent exists**: `getAllToolDefinitions` strips blocked tools and privacy-narrows `get_conversation_messages` for remote exposure.

## 3. The mapping — composition, not port

The two systems disagree on where the human gate lives: CodFlow's doctrine is *annotate-and-trust-client* (surface + consent + audit, execution immediate); SahelFlow's is *server-side HITL* (propose → digest-bound person approval → kernel execute) even for its own chat UI. The mapping is therefore a **composition**: adopt CodFlow's surface conventions (registry shape, scope hiding, declared outputs, derived annotations), but every destructive verb rides SahelFlow's proposal-bound path — the proposal gate **replaces**, not supplements, client-side confirmation.

**Class-by-class:**

| Tool class | Surface behavior under the mapping | Human gate |
| --- | --- | --- |
| `read` (19) | Direct execute, scope-hidden, rate-limited, audited (CodFlow's model verbatim) | None beyond authority + audit |
| `external_read` (2) | Same, with the `getAllToolDefinitions` privacy narrowing applied | None |
| `sensitive` (8) | Tool executes nothing: returns `{ pending_action_proposal: true, tool, proposal, proposalDigest }` — exactly today's chat-registry result shape. The MCP client **cannot** approve; the human approves in the dashboard Agents workspace (`POST /api/ai/actions/[id]/approve` with the digest) | **Server-side proposal** (10-min TTL, digest-bound, person-only) |
| `blocked` (1) | Never advertised (CodFlow's registration-time hiding makes this trivial) | — |

**Vocabulary crosswalk (verified both sides):** `create_order`↔`createOrder`, `update_order_status`↔`updateOrderStatus`+`recordOrderProductReturn`, `update_product_stock`↔`adjustProductStock`/`adjustVariantStock`, `create_product`↔`createNewProduct`, `update_product_price`↔(subset of) `updateProductDetails`, `create_customer`↔`createNewCustomer`, `update_customer_notes`↔(subset of) `updateCustomerProfile`, `cancel_order`↔*no CodFlow equivalent* (its `deleteOrder` is a destructive delete, not a lifecycle cancel — the two systems diverge here and the divergence is correct for COD truth). The 19 read tools cover the same ground as CodFlow's list/get families with different names; the crosswalk table is mechanical. **What does not map:** CodFlow's delete verbs (`deleteCustomer`, `deleteProduct`, `deleteLandingPage`, …) — SahelFlow's AI vocabulary has no deletes, and adding one is a new policy entry + a Founder decision, not a default; driver settlements and shipping-profile overrides (SahelFlow's delivery authority model differs); plan gating (N/A).

**Registry & scopes:** adopt the `TOOL_REGISTRY`-style entry list (`requires` + build) keyed on **SahelFlow's existing `Phase2Action` permissions** (resolved through `resolvePhase2Permissions`, deny-by-default) rather than minting a parallel `domain:action` OAuth vocabulary — one vocabulary, zero drift, owner role as the ceiling. Visibility = registration-time hiding, fail-closed on no trusted actor. Extending the vocabulary = one policy entry + executor case + target snapshot + test pin (the extension path is already proven by the 8 sensitive verbs).

**Outputs & annotations:** adopt `toolOutput()`'s success/failure union with per-tool `outputSchema` + `structuredContent` safe-parse-with-text-fallback, `limit`/`offset`+`count` pagination, 200/60 s fail-open rate limiting (local equivalent), and the **derived-annotations + golden-test** pattern (`destructiveHint` on the 8 sensitive verbs as UX framing only — the server gate is the actual human gate; mislabeling fails CI).

**Transport & auth (the real fork in the road):** SahelFlow is local-first; the natural shape is a **local sidecar endpoint** (stdio or localhost streamable HTTP) speaking to the trusted-actor model — not a public OAuth worker. The one genuinely missing component is the ingress that mints a durable `TrustedActorContext`/person actor for an external agent session (everything today assumes a local dashboard session); it must bind the agent to a non-person actor for *requests* while approval stays strictly person-held (`approvals.approve`), keeping an agent never-approver. CodFlow's OAuth/consent/revocation stack belongs to the hosted control plane and is **#230-gated** — it feeds EX-6, not this surface.

## 4. Decision points recorded for the Founder (design input only)

1. **Transport**: local sidecar endpoint (no #230 dependency, offline-first) vs control-plane-hosted (fully blocked until #230's owned-domain gate). The study assumes sidecar if anything ships.
2. **Vocabulary scope**: the 8 sensitive verbs as-is, or extend (deletes, settlements) — extension is a new explicit decision per verb.
3. **Scope vocabulary**: reuse `Phase2Action` (recommended — single authority) vs new `mcp:*` scopes.
4. **Confirmation doctrine**: keep the server-side proposal gate as the *only* human gate; treat client confirmations as optional UX (recommended — CodFlow's rolled-back elicitation is the cautionary evidence).
5. **Audit shape**: per-invocation `via:"mcp"` audit rows with >1024-char redaction, riding the kernel's existing audit channel.

No code, route, dependency or schema change is authorized or proposed by this document; conversion requires the Founder's explicit agent-surface decision, and FRC-5's external gates are unaffected.
