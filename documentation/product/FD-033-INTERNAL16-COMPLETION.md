# FD-033 — Internal.16 completion convergence, first-revenue bootstrap and whole-product assurance

> **Status:** Founder-approved binding decision
> **Date:** 2026-08-13
> **Applies to:** the exact post-Internal.15 completion program culminating in `1.0.0-internal.16` / MSI `1.0.0.16`
> **Supersedes only:** lower execution-order/cadence instructions that would force the remaining Phase 5/6/7 adoption and Phase 8 implementation into repeated small release loops before Internal.16. It does not weaken Phase 1–4 authority, P0/P1 blocking, preservation, security/privacy, provider truth, installed evidence, customer-online issue #230, representative beta, external review or Stable gates.

The Founder has directed an emergency completion-and-first-revenue convergence with a 24-hour operating window beginning 2026-08-13. The commercial constraint is zero paid marketing/infrastructure budget before first revenue and a near-term objective of at least USD 100 equivalent collected revenue. Commercial urgency changes execution economics and sequencing; it never authorizes fabricated readiness or a lower product-quality bar.

## 1. Internal.16 is the complete-product candidate

Internal.15 remains the exact FD-032 Founder-only offline checkpoint. Internal.16 is intentionally different: it is built as the first complete SahelFlow application candidate rather than another partial route or subsystem checkpoint.

Internal.16 must converge, in one controlled implementation frontier:

- remaining Phase 5 whole-product AAA route adoption;
- remaining Phase 6 Arabic/RTL/accessibility closure;
- remaining Phase 7 performance/reliability implementation and certification work;
- full Phase 8 connected-platform implementation;
- delivery-provider cleanup and first-class EcoTrack Pro integration;
- AI workspace, order-extraction and AI-tool quality/performance hardening;
- release, updater, recovery, licensing, cloud, privacy/security and whole-product verification required for a user-ready candidate.

This decision changes the implementation sequence for exact Internal.16. It does **not** mark any unfinished Phase 5/6/7/8 gate as passed. Those obligations become integrated Internal.16 acceptance gates and must be objectively satisfied before a user-ready claim.

## 2. One large implementation wave; no repetitive micro-release loop

The Internal.16 execution model is:

```text
reconstruct exact post-Internal.15 authority
→ complete one whole-product reconnaissance
→ freeze one consolidated Problem Register
→ freeze shared contracts and non-goals
→ implement one large dependency-correct completion wave
→ use cheap targeted checks while coding
→ freeze the complete Internal.16 candidate
→ run one deep whole-product certification pass
→ produce one consolidated findings/repair batch
→ run the affected proof plus one final complete certification pass
→ publish the signed Internal.16 updater only if the evidence supports it
```

During the implementation wave:

- do not run a full MSI/replacement-install/eight-hour/whole-repository release cycle after every small edit;
- do run targeted type, lint, unit, contract, database, browser or Rust checks needed to prevent long-lived broken code;
- group fixes by root cause and affected authority rather than screenshot or assertion order;
- push coherent implementation batches, not every tiny edit;
- never rerun an unchanged passing head;
- never retry a deterministic product failure until it turns green without explaining and fixing the cause;
- a proven P0 may interrupt the wave immediately; a proven P1 must be closed before candidate freeze/release.

Once the Internal.16 candidate is frozen, feature expansion stops. Certification and consolidated repair own the remainder of the cycle.

For Internal.16, every user-facing Required feature/function must either work completely at its declared authority or be removed from the user-facing promise. The candidate may not contain knowingly fake controls, dead navigation, decorative metrics presented as truth, disconnected settings, demo-only success, hidden legacy authority, unlocalized operational copy, or actions that report success before canonical commit.

Completion must cover at least:

- installer, startup, authenticated workspace, updater and close/reopen;
- trial/permanent licensing, activation, expiry, recovery and transfer boundaries;
- multi-shop and team identity/permission/revocation;
- products, inventory and stock authority;
- customers, risk and history;
- orders, confirmation, fulfillment and Golden COD transitions;
- courier delivery, returns and reconciliation;
- COD/accounting and financial projections;
- Inbox/WhatsApp and durable provider effects;
- AI Agents, extraction, tools and approval-bound actions;
- automations and durable recovery;
- analytics, charts and operational reporting;
- settings, secrets, backup/restore/export/destructive ceremonies;
- AR/FR/EN, RTL/LTR/mixed content, themes, density, motion, keyboard/focus, zoom/reflow, reduced motion and low-end behavior;
- Phase 8 remote work, storefront, PWA, cloud control, zero-knowledge backup transport and Founder operations.

No Phase 1–4 canonical business/data/security authority may be rewritten merely for visual or schedule convenience.

## 4. Phase 8 must be implemented completely

Internal.16 must implement the Phase 8 connected platform as one coherent system around desktop canonical authority:

- authenticated encrypted projection/command protocol;
- remote success only after canonical desktop commit;
- shared multi-tenant Cloudflare control plane;
- hosted storefront with durable checkout receipt and atomic publish/rollback;
- operational PWA/browser companion within desktop-owned authority;
- zero-knowledge encrypted backup transport with quotas/retention authority;
- private Founder Console with bounded metadata and offline permanent-signing separation;
- tenant isolation, replay/duplicate protection, outage behavior, abuse/rate/cost controls and measurable quotas.

Cloud outage must not corrupt or block valid permanent local work. SahelFlow/Cloudflare alone must not be able to decrypt seller backups. Storefront success must correspond to a durable receipt. Cross-tenant leakage and duplicate irreversible external effects are release-blocking.

## 5. Cloudflare first-revenue bootstrap

FD-005/FD-019 shared-cloud architecture remains. For the pre-revenue bootstrap only, the Founder authorizes starting within the currently available Cloudflare Free allowances when measured capacity is sufficient for the first prospect/buyer.

Rules:

- desktop remains canonical; the free tier does not justify moving operational truth to cloud;
- Workers remain thin and bounded; heavy work is not hidden in unbounded request CPU;
- D1/R2/other services are metered and quotas are observed before user release;
- the first collected sale/reservation may fund the SahelFlow-owned domain and any paid Cloudflare capacity that measured usage actually requires;
- `workers.dev`, `pages.dev` or another provider hostname does **not** substitute for the SahelFlow-owned production-domain requirement;
- if money is collected before the domain exists, it is a reservation/payment step, not evidence that the customer-online production boundary passed.

Issue #230 remains a P1 customer-online release boundary: owned domain, distinct primary/recovery HTTPS ingress, protected production bindings, representative Algerian fixed/mobile reachability, forced recovery and signed installed customer-trial evidence remain required before the online-trial/public customer-release claim.

FD-012 launch pricing remains unchanged unless a later Founder decision changes it. The USD 100-equivalent objective is a cash objective, not a new product price.

## 6. NOEST/Nord et Ouest removal and EcoTrack Pro

Internal.16 removes NOEST/Nord et Ouest Express as a supported runtime provider identity and replaces that surface with a first-class EcoTrack Pro integration.

Required EcoTrack outcomes:

- canonical provider ID and capability contract owned by EcoTrack, not a renamed NOEST label;
- encrypted credential/endpoint configuration through the protected secret architecture;
- connection/capability validation;
- shipment creation and provider-required validation/commit semantics;
- home/office or other supported fulfillment modes from the authoritative current contract;
- COD amount, recipient, wilaya/commune/address, weight, notes and exchange metadata where supported;
- tracking/status-history normalization without losing provider detail;
- tariff/cost lookup and location/reference data where supported;
- cancellation/update/re-dispatch/return behavior only where the authoritative API supports it;
- labels/bordereaux or merchant documents where the authoritative API exposes them;
- exact timeout/retry/ambiguous-outcome semantics and durable reconciliation so a lost response cannot silently create a duplicate parcel;
- deterministic conformance tests plus live certification state separated from source/conformance state.

No endpoint or capability may be guessed. The implementation must use current official/provider-issued EcoTrack Pro merchant documentation. Real credentials stay out of source/chat/issues/tests. If a live account is not yet available, FD-030 still allows source/conformance completion while the UI truthfully distinguishes that state from live-certified.

Historical records that store `noest` must remain readable. Migration/compatibility must not silently reinterpret historical provider identity or reuse secrets unless the exact credential/contract mapping is proven safe.

## 8. Order extraction quality, accuracy and performance

Internal.16 must treat order extraction as a measurable operational capability, not a best-effort AI demo.

The existing regex/Gemini smart-routing and extraction-metric paths must be audited end to end. Certification requires a representative held-out corpus covering Algerian seller reality, including:

- Arabic, French, English, Algerian Darija and mixed-script/mixed-language messages;
- noisy WhatsApp-style punctuation/spacing/phone formats;
- product names/variants, quantity, price/COD amount, recipient name/phone, wilaya, commune/address, notes and supported delivery mode;
- complete, partial, contradictory, ambiguous and non-order messages.

Measure and retain:

- field-level exactness/normalization accuracy;
- required-field completeness;
- false-complete rate;
- confidence calibration and missing-field truth;
- regex-versus-Gemini routing correctness;
- offline/no-key fallback behavior;
- malformed/model-invalid response handling;
- quota/rate-limit behavior;
- per-path and end-to-end latency distributions;
- correction/review behavior before canonical order creation.

Low confidence or missing Required fields must result in explicit review/repair, never invented order truth. Model output does not bypass canonical order validation, seller review where required, idempotency, pricing, risk, inventory or business-command authority.

## 9. AI tool correctness and performance

Every AI tool/action available to the model must be inventoried and certified.

For each tool, prove:

- schema/argument validation;
- correct shop, actor, permission and license authority;
- proposal/approval binding for sensitive actions;
- exact target/version revalidation before mutation;
- deterministic read/mutation result shape;
- idempotency/duplicate protection where applicable;
- timeout, cancellation, retry and ambiguous external-effect handling;
- localized seller-facing result/error state;
- no raw secrets/PII leakage into diagnostics or model context beyond approved policy;
- latency split between SahelFlow overhead, local database/business execution and unavoidable external/model/provider latency;
- bounded concurrency/resource impact on T470/floor hardware.

Local tool dispatch/validation must not become a perceptible bottleneck relative to the existing Phase 7 local interaction budgets. External/model latency is measured separately and must surface honest progress/degraded states rather than freezing the workspace or reporting fabricated success.

## 10. Internal.16 assurance standard

The Founder's “99.99% sure” objective means aggressive evidence-backed confidence, not a mathematical warranty that no unknown software defect can exist.

Before the first production buyer receives the Internal.16 application, the frozen candidate must have:

- 100% of the defined Required feature/journey matrix executed at the applicable layer;
- zero known P0/P1 product, data, money, security, recovery, accessibility, localization or reliability defect;
- complete source/authority/type/lint/unit/integration/database/browser/Rust/Windows selected gates;
- clean install plus Internal.15 → Internal.16 in-place updater proof with AppData/key/database preservation;
- Golden COD, provider-effect, AI extraction/tool and automation journeys;
- backup/restore/replacement-install/migration interruption proof;
- licensing/trial/permanent/recovery/expiry behavior appropriate to the candidate release mode;
- AR/FR/EN, RTL, mixed direction, keyboard, zoom/reflow and reduced-motion proof;
- T470/floor performance budgets and the required eight-hour stability/resource trend on the final candidate;
- Phase 8 outage/replay/rollback/tenant-isolation/storefront/remote/zero-knowledge-backup journeys;
- one complete frozen-head adversarial review, one consolidated repair batch if needed, and a final complete verification of the repaired candidate.

A material change after the final freeze invalidates the affected evidence and requires proportionate rerun. Unchanged passing evidence is not repeated for ritual.

External/provider/legal/representative-beta gates remain truthfully distinct. Internal.16 may be the complete product/RC or a paid Beta candidate only to the extent its evidence supports that claim. Stable still requires the applicable Phase 9 external and Founder-promotion gates; schedule pressure may not relabel missing external evidence as passed.
