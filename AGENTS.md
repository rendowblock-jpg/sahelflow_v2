## Professional cross-session execution protocol

This protocol records the working style explicitly approved by the Founder on
2026-07-31. Every new session must follow it.

### Reconstruct before writing

- Verify protected `main`, PR #195, the exact branch head and its latest checks.
- Read Working Memory and the current PR body before deciding what remains.
- Inspect exact source/tests for the active package.
- Never infer another active agent from branch movement. State another owner only
  when GitHub or the Founder explicitly proves one.
- Preserve all unrelated user work, local worktrees and canonical AppData.

### Build coherent outcomes, not file-sized tasks

- Keep one active Phase 1 closure frontier at a time.
- Finish a package across its applicable schema, migration, command, API, UI,
  recovery, AR/FR/EN and invariant-test boundaries.
- Push coherent batches. Do not create a status/review/CI loop after every small
  edit.
- Do not weaken production authority to satisfy a stale test; update the stale
  compatibility test or remove the superseded path.
- CI must remain read-only. Never leave a self-modifying workflow, branch-writing
  token or temporary repair step in the repository.

### Validation cadence

- Use local/static reasoning while assembling the package.
- Run one draft source checkpoint when the coherent package is assembled.
- Repair only concrete diagnostics from that exact head.
- Record a package as source-complete only after Prisma generation, authority/docs,
  TypeScript, ESLint, the full unit/integration suite and migration status pass.
- Defer Windows/Rust/MSI validation until the declared multi-phase source is frozen,
  except where a phase exit explicitly requires a bounded platform fixture.

### Communication cadence

- Report at package start, a meaningful completed milestone, a concrete blocker,
  and session close.
- Do not narrate every file edit.
- Do not remain silent through a long material operation; provide a brief factual
  checkpoint when the user is waiting.
- Never call a package or phase complete before its named evidence is green.

### Session close and resume

At the end of every substantial session:

1. stop at a coherent repository state rather than halfway through a dangerous
   transaction or migration;
2. remove temporary workflows, scripts, broad permissions and repair scaffolding;
3. update `documentation/operations/WORKING_MEMORY.md` with the exact frontier;
4. update the PR body with completed packages, latest evidence and the single next
   package;
5. keep the PR draft unless the full declared program is ready for the frozen-head
   merge cycle;
6. leave one explicit next-session order that can be reconstructed without chat;
7. use existing authorities only—do not create another permanent handoff document.

A new session resumes the same branch and PR. It does not restart planning, reopen
completed packages or create a parallel completion branch.

## Review severity

- **P0:** active data loss, secret exposure, cross-shop/tenant effect, corrupt
  update/restore or irreversible stock/money damage. Stop immediately.
- **P1:** required journey or authority failure, negative/double stock, incorrect
  money, duplicate/lost effect, unsafe migration, startup/install/recovery
  failure, or major unusable Arabic/UX/accessibility defect. Blocks merge/release.
- **P2:** bounded material hardening with a safe workaround.
- **P3:** low-impact polish.

P2/P3 are owned follow-ups. They do not create unbounded review loops.

## Shared validation commands

GitHub Actions uses commands including:

```bash
bun run sf-version
bun run sf-audit
bun run sf-inventory
bun run sf-verify
bun run sf-verify --fast
```

These commands prove only what they execute. Linux/source checks cannot prove
installed Windows, T470, provider, legal or Beta behavior.

## Milestone release truth

Routine Internal candidates remain draft until every selected signed post-build
gate passes. The protected workflow verifies exact source, signed MSI, signature,
staged/installed runtime, authenticated UI, evidence, updater metadata and the
source-bound release tag before automatic publication.

`latest.json` is updater metadata that contains the signature for the signed MSI;
do not call the JSON document independently signed unless explicit manifest
signing is implemented.

Failed candidates remain drafts. Beta and Stable always require explicit Founder
promotion.
